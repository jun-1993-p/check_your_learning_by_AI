# 빈칸 검증: LLM이 쓴 빈칸은 하나만, 긴 밑줄은 하나로

Status: ready-for-agent

## Problem Statement

학습자가 확인 퀴즈에서 빈칸 문제를 받았는데, 빈칸마다 무엇을 써야 할지 알 수 없는 문제가 나와요. 예를 들어 `딕셔너리 ____에서 '____'의 Value를 얻기 위해 ____['____']을 사용한다.`는 빈칸이 4개이고 정답은 `a` 하나예요. 정답을 모든 빈칸에 넣으면 우연히 말이 되긴 하지만, 학습자는 각 빈칸에 서로 다른 말이 들어간다고 읽게 돼요.

또 LLM이 정답 자리를 `________`처럼 긴 밑줄로 쓰면 빈칸 2개로 세어져요. 채운 문장은 "지운다지운다"가 돼서 문제와 정답이 어긋나요.

두 경우 모두 지금 검증을 통과해요. 그래서 앱 퀴즈·시연 GUI·정확도 평가에 그대로 나와요. Ollama 모델에서 처음 봤지만 Groq gpt-oss-20b에서도 나타났어요 (`.idea_folder/데모_LLM_모델비교_20261013.md` 5장).

## Solution

빈칸 문제를 만드는 공용 함수 하나에서 두 가지를 바로잡아요.

1. LLM이 쓴 밑줄 덩어리(밑줄 3개 이상)는 길이와 관계없이 빈칸 하나로 바꿔요.
2. 정규화한 뒤 LLM이 직접 쓴 빈칸이 2개 이상이면 출제 오류로 거절해요. 문제는 정해진 재시도 흐름대로 다음 문단으로 넘어가요.

같은 정답 단어가 문장의 다른 곳에도 나오면 지금처럼 코드가 그 자리도 가려요. 그래서 "같은 단어는 함께 가린다"는 기존 규칙은 유지되고, 여러 빈칸이 있어도 모두 같은 말이 들어가는 것이 코드로 보장돼요. 학습자는 빈칸이 여러 개인 문제를 받으면 모두 같은 답이라고 믿을 수 있어요.

## User Stories

1. 학습자로서, 빈칸이 하나인 문제를 받고 싶어요. 그래야 무엇을 채워야 하는지 헷갈리지 않아요.
2. 학습자로서, 빈칸이 여러 개라면 모두 같은 말이 들어가는 문제만 받고 싶어요. 그래야 정답 하나로 문장이 온전히 완성돼요.
3. 학습자로서, 빈칸에 정답을 넣은 문장이 자연스럽게 읽히길 바라요. 그래야 해설을 볼 때 "지운다지운다" 같은 어색한 문장에 혼란스럽지 않아요.
4. 학습자로서, 빈칸 개수 표시가 실제 빈칸 수와 같길 바라요. 그래야 화면의 안내를 믿을 수 있어요.
5. 학습자로서, 잘못 만든 문제 대신 다른 문단에서 다시 만든 문제를 받고 싶어요. 그래야 확인 퀴즈의 문제 수가 크게 줄지 않아요.
6. 학습자로서, 직접 풀기(`--solve`)에서 빈칸 문제를 채점받을 때 정답 목록 대조가 의미 있길 바라요. 그래야 맞게 쓴 답이 오답으로 보이지 않아요.
7. 시연자로서, 시연 GUI의 빈칸 1문제가 엉뚱한 여러 빈칸 문제로 나오지 않길 바라요. 그래야 시연 중에 설명하기 어려운 문제를 피할 수 있어요.
8. 시연자로서, 어떤 LLM 공급자(Groq, NVIDIA, Ollama)를 고르든 같은 검증을 거치길 바라요. 그래야 공급자를 바꿔도 품질 기준이 같아요.
9. 개발자로서, 앱 퀴즈와 정확도 평가가 같은 빈칸 규칙을 쓰길 바라요. 그래야 평가 결과가 앱 품질을 대변해요.
10. 개발자로서, 거절된 빈칸 문제의 사유가 로그에 남길 바라요. 그래야 어떤 모델이 이 오류를 자주 내는지 알 수 있어요.
11. 개발자로서, LLM이 `___`, `____`, `________`처럼 어떤 길이로 밑줄을 써도 같은 빈칸으로 처리되길 바라요. 그래야 모델마다 다른 버릇에 흔들리지 않아요.
12. 개발자로서, 정답이 문장에 그대로 남아 있으면 지금처럼 코드가 그 자리도 가려 주길 바라요. 그래야 정답 노출을 막을 수 있어요.
13. 개발자로서, 파이썬 이름에 들어간 밑줄(`__init__`, `snake_case`)은 빈칸으로 바뀌지 않길 바라요. 그래야 정상 문제가 잘못 거절되지 않아요.
14. 개발자로서, 프롬프트에서도 빈칸은 하나만 쓰라고 안내하길 바라요. 그래야 거절과 재시도로 쓰는 LLM 호출이 줄어요.
15. 개발자로서, 이 규칙을 LLM 호출 없이 빠르게 확인하는 테스트가 있길 바라요. 그래야 나중에 규칙을 고쳐도 회귀를 바로 알 수 있어요.
16. 평가자로서, 정확도 평가의 빈칸 문제도 같은 규칙으로 걸러지길 바라요. 그래야 사람이 판정할 문제에 이런 결함이 섞이지 않아요.
17. 평가자로서, 이 오류로 거절된 문단은 다른 출제 오류와 같은 방식으로 기록되길 바라요. 그래야 결과 CSV 형식이 바뀌지 않아요.

## Implementation Decisions

- **수정 위치는 빈칸 문제를 만드는 공용 함수(`quiz_templates.make_question`) 하나예요.** 앱 경로(근거 검사 함수 → `quiz_session`, 시연 GUI)와 평가 경로(`eval_blank`의 문단 검증)가 모두 이 함수를 거쳐요. 함수의 이름과 반환 형태 `(빈칸 문제, 빈칸 수)`, 실패 시 `BlankError`를 던지는 계약은 바꾸지 않아요.
- **처리 순서**
  1. LLM이 쓴 문장에서 밑줄 3개 이상의 덩어리를 빈칸 표시(`____`) 하나로 바꿔요.
  2. 빈칸 표시가 없으면 지금처럼 문장에서 정답을 찾아 직접 가려요.
  3. 빈칸 표시가 2개 이상이면 `BlankError`("LLM이 쓴 빈칸이 N개" 같은 사유)를 던져요.
  4. 빈칸이 1개면 지금처럼 문장에 남은 정답 단어를 모두 가리고, 최종 빈칸 수를 돌려줘요.
- **밑줄 기준은 3개 이상이에요.** 보고서 제안은 4개 이상이었지만 `___`(3개)도 빈칸으로 보는 편이 안전해요. 다만 앞뒤에 영문자·숫자가 붙은 밑줄(`a___b`, `___private`, `__init___`)은 이름의 일부라 빈칸으로 보지 않아요 (02 리뷰에서 추가).
- **빈칸 2개 이상을 근거 인용과 대조해 허용하는 안은 채택하지 않아요.** LLM이 쓰는 문장은 문단을 그대로 복사한 것이 아니라 새 문장이라 대조 기준이 불안정하고, 평가 경로에는 근거 인용이 없어요.
- **프롬프트 안내를 맞춰요.** 빈칸 유형 지시문(`quiz_templates`의 유형별 지시)에 "정답 자리는 `____` 하나로만 쓰고, 같은 단어가 또 나오면 그대로 둬(코드가 가린다)"는 취지를 넣어요. 평가 프롬프트에도 같은 취지가 없다면 맞춰요. 풀이 LLM 프롬프트("빈칸이 여러 개면 같은 말이 모두 들어가")는 그대로 맞는 설명이라 두어요.
- **거절된 문제의 처리 흐름은 바꾸지 않아요.** 앱은 "빈칸 오류(…)"로 기록하고 같은 출처의 다음 문단으로 재시도해요(최대 3번). 평가는 기존 `BlankError` 처리대로 다음 순위로 넘어가요. 결과 CSV 열은 그대로예요.
- ADR 0005(문단 하나 → LLM 문제 하나, 근거 인용 검사)와 충돌하지 않아요. 출제 못함이 늘어날 수 있지만, ADR 0005대로 폴백은 추가하지 않아요.

## Testing Decisions

- **좋은 테스트는 겉으로 드러나는 동작만 봐요.** 입력 `(LLM이 쓴 문장, 정답)`에 대해 돌려받은 `(문제, 빈칸 수)`나 `BlankError` 여부만 확인하고, 내부 정규식이나 도우미 함수는 직접 검사하지 않아요.
- **테스트 지점은 `make_question` 하나예요.** 앱과 평가가 모두 이 함수를 거치므로 여기서 확인하면 두 경로가 함께 보장돼요. LLM·Chroma·임베딩 모델 없이 순수 함수로 돌아가요.
- **새 테스트 파일 하나를 표준 라이브러리 `unittest`로 만들어요.** 추가 설치가 필요 없고, 프로젝트 루트에서 `python -m unittest`로 돌려요. 프로젝트 첫 테스트라 앞선 예가 없어요. 품질 평가(`evals/eval_blank.py`)는 LLM을 부르는 통합 평가라 성격이 달라요.
- **확인할 사례**
  - 빈칸 하나 + 정답이 문장에 다시 나오지 않음 → 그대로, 빈칸 수 1
  - 빈칸 하나 + 정답이 문장에 또 나옴 → 그 자리도 가려져 빈칸 수 2, 채우면 같은 말
  - 긴 밑줄 하나(`________`) → 빈칸 하나로 바뀌고 빈칸 수 1, 채운 문장에 정답이 한 번만 들어감
  - `___`(3개) → 빈칸으로 인정
  - LLM이 쓴 빈칸 2개 이상(보고서의 딕셔너리 예) → `BlankError`
  - 긴 밑줄 2덩어리 → `BlankError`
  - `__init__`, `snake_case` 같은 이름이 든 문장 → 빈칸으로 바뀌지 않음
  - 빈칸 없음 → 지금처럼 정답을 찾아 가림 (기존 동작 회귀 확인)
  - 기존 오류(정답 비어 있음, 너무 긴 정답, 빈칸 말고 내용 없음) → 계속 `BlankError`
- Ruff(`ruff check`, `ruff format`)를 통과해야 해요.

## Out of Scope

- 단답형 실패(정답 노출·개념 불일치), 사용자 결정으로 보류 중이에요.
- 빈칸 정답의 의미 판정(목록에 없는 답을 LLM이 판정하는 채점 단계)
- 코드 포함 출제 (ADR 0003)
- 출제 못함을 줄이는 폴백이나 재시도 횟수 변경 (ADR 0005)
- 검색 거리 기준 재측정 (`.scratch/keyword-search-threshold`)
- 실제 LLM으로 다시 측정하는 평가 실행. 필요하면 별도로 범위를 확인받아요.
